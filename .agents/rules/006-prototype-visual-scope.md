# 로컬 시각 프로토타입 범위 규칙

이 규칙은 CardFit **최초 경량 시각 체크포인트**에만 적용된다. 계획 정본은 19건을 유지하는 `TASK/task1/prototype-suggestion.md`이고, 구체 시각화 계획은 `TASK/task1/prototype-visual-spec.md`다.

## 착수 가능 TASK

계획 정본은 계약 8건·UX 4건·UI 7건의 19건이다. 최초 코딩은 `P-VIS-01~03`만 수행하고 `UX-001~004`, `UI-001·003·005·006`의 최소 조항만 참조한다. 원 TASK를 `Done`으로 닫지 않는다.

- 구현: 최소 기반, SINGLE 미래지출 입력, 세 시나리오 유지·변경 결과, 정형 근거 6개
- 연기: `UI-002·004·007`, RANGE, AI, 상태 7종 전체, 조합 저장·외부 이동, 검토자 상태 패널
- 계약 8건은 19건 계획에서 유지하며 최초 시각 방향 승인 후 정본 의존 순서로 진행한다.

## 코드 거처와 실행

- 프로토타입 앱은 **저장소 루트의 Next.js App Router 앱 하나**다. `prototype/` 등 별도 앱, 별도 저장소, 정적 HTML 프로토타입을 만들지 않는다.
- 스택은 TypeScript · Tailwind CSS · shadcn/ui로 고정한다. 패키지 매니저는 `npm`이고 `npm run dev`로 실행한다.
- `src/` 디렉터리를 만들지 않고 루트 `app/`을 사용한다. 공통 UI는 `components/`, 타입·로더는 `lib/`, Fixture는 `fixtures/`에 둔다.
- 이 단계에서는 Route Handler·Server Action·Prisma·Supabase·인증·미들웨어·배포 설정을 작성하거나 연결하지 않는다.

## ViewModel 타입 규칙

- 화면이 바인딩하는 데이터 모양은 `features/cardfit-prototype/lib/view-model.ts`를 단일 진입점으로 삼고, `prototype-visual-spec.md` §4의 **ViewModel 타입 스케치**를 따른다.
- 컴포넌트 파일 안에 화면 전용 데이터 타입을 인라인으로 정의하지 않는다.
- 이 타입 스케치는 `SPEC-001` 승인 계약이 아니라 **후보**다. 파일 상단에 그 사실을 주석으로 남긴다.
- Fixture와 화면이 어긋나면 화면이 아니라 타입 스케치와 Fixture를 먼저 고친다.
- 온보딩·입력·결과 모델은 기능별로 구분하고 `loading`, `empty`, `partial`, `stale`, `error`, `unavailable`, `success` 공통 상태 타입을 조합한다.
- Fixture에는 `fixtureId`, `status`, `isExample: true` 메타데이터를 포함한다.

## 라우팅 규칙

- 최초 체크포인트의 주요 라우트는 `/plan`, `/result` 두 개다.
- 계산 진행·데이터 품질·세 시나리오·근거·선택 화면은 의미상 속한 주요 라우트 내부의 명시적 ViewModel 상태로 전환한다.
- 상태마다 임의의 별도 페이지를 추가하지 않는다. 새 주요 라우트가 필요하면 `prototype-visual-spec.md`와 Grill Ledger에서 먼저 결정한다.
- `/`와 `/onboarding`은 후속 체크포인트 전까지 만들지 않는다.

## Fixture와 검토 모드 규칙

- Fixture는 `features/cardfit-prototype/fixtures/`의 TypeScript 모듈로 두고 `features/cardfit-prototype/lib/view-model.ts`의 타입을 만족시킨다.
- 상태별 직접 접근은 허용된 `state` query로 재현하며, 알 수 없는 값은 대표 Fixture로 되돌린다.
- 일반 사용자 UI에는 데이터 상태 선택기를 노출하지 않는다.
- `review=1` 검토 패널은 최초 체크포인트에서 구현하지 않는다.
- 사용자 인터뷰 참가자는 패널을 조작하지 않는다. 진행자가 상태별 URL을 준비한다.
- 검토 패널은 실제 서비스 기능으로 승격하지 않으며 본 개발 전환 Gate에서 제거 여부를 확인한다.

## 상태 언어와 문체 규칙

- 공통 상태는 `prototype-visual-spec.md` §6의 7종 상태 사전과 대표 제목·CTA를 따른다.
- 상태 제목·진행 상태·일반 안내는 차분한 해요체, 계산 사실·데이터 기준·금융 조건·스코프·주의사항은 합니다체를 사용한다.
- CTA는 행동형 명사구로 작성한다.
- `partial`에서는 추천 결과를 노출하지 않고, `stale`에서는 데이터 기준일을 반드시 함께 표시한다.
- 혜택·정확성·발급 가능성을 보장하거나 사용자를 탓하는 표현을 사용하지 않는다.

## 스코프 고지 규칙

- 온보딩·조합 선택·외부 이동에는 `prototype-visual-spec.md` §7의 후보 고지를 그대로 사용한다.
- 후보 고지는 `COMMAND-008` 승인 계약이 아니며, 본 개발에서 승인 문구가 확정되면 교체한다.
- 카드 신청·발급·해지 대행, 확정 혜택·수익, 외부 처리 완료를 암시하는 문구를 사용하지 않는다.
- 조합 저장 완료와 실제 카드 신청·발급·해지 완료를 동일한 상태로 표현하지 않는다.

## 입력 초기값 규칙

- 실제 개인 데이터가 없거나 과거 이력이 부족한 경우 미래지출 금액은 빈 값으로 시작한다.
- 사용자가 명시적으로 선택한 경우에만 수정 가능한 비개인화 예시 값을 적용한다.
- 예시 값은 개인 소비 데이터나 업계 통계를 기준으로 하지 않았음을 입력 영역 가까이에 표시한다.
- 승인된 출처·기준일·최신성·편향 검토 없이 `업계 평균`이라는 명칭이나 값을 사용하지 않는다.
- 업계 평균 분기는 M2 별도 변경 요청과 승인 전에는 활성화하지 않는다.

## 입력 조작 규칙

- `/plan`은 미래지출 입력과 카드 조건 확인의 2단계이며 `SINGLE`을 기본으로 한다. `RANGE`는 사용자 선택 시 같은 화면에서 펼친다.
- 카테고리는 `prototype-visual-spec.md` §8의 선택형 대분류를 사용하고 `기타`에서만 직접 입력을 허용한다.
- 금액은 만원 단위로 고정해 입력하고 전체 원 금액과 필요한 경우 억 단위 읽기 표현을 병기한다. 단위 전환 탭과 소수 입력을 만들지 않는다.
- 빠른 금액 추가·실행 취소·금액 지우기와 모바일 숫자 키패드를 제공한다.
- RANGE의 `최소 ≤ 예상 ≤ 최대`를 입력 중 검증하고 오류 상태에서도 입력값을 보존한다.
- 프로토타입에서 일시불·할부 선택과 할부 개월을 입력받거나 할부 계산 지원을 암시하지 않는다.
- 결과 근거에는 할부 수수료·월별 실적 반영 차이·카드사별 무이자 할부 조건을 미반영 항목으로 표시한다.
- 미래지출은 다건 입력을 지원하고 각 항목에서 `ONE_TIME`·`MONTHLY` 지출 형태와 연·월 단위 시점을 받는다.
- 증가·감소를 직접 선택하게 하지 않는다. 비교 가능한 과거 월평균 Fixture가 있을 때만 미래 월 금액과의 방향·차액을 표시한다.
- 과거 기준값이 없으면 방향을 생성하지 않으며, 값이 미정인 `confidence` 입력을 프로토타입에 추가하지 않는다.
- 최대 입력 금액·카테고리별 상한·지출 형태별 상한을 임의로 정하지 않으며 프로토타입에서는 빈 값·0원·음수·비숫자·RANGE 순서만 검증한다.

## 결과 시나리오 규칙

- 시나리오 탭의 화면 라벨은 `더 적게`·`예상한 만큼`·`더 많이`, 내부 값은 `LOW`·`BASE`·`HIGH`를 사용하며 `BASE`를 기본 선택한다.
- 접근성 이름과 결과 설명에는 예상 지출과의 관계를 포함한다. 선택 상태를 색상에만 의존해 표시하지 않는다.
- 현재 조합과 변경 조합의 계산 결과가 같으면 `유지`로 분류하되 우월성을 주장하지 않고 예상 혜택 차이가 없다고 설명한다.
- `유지`와 `변경`은 같은 위계의 정상 결과로 표시하고 변경을 성공 상태처럼 강조하지 않는다.
- 최초 체크포인트에서는 다중 변경 후보 순위를 표시하지 않으며, 동률 후보의 정렬·대표 선택·`1위`·`최적` 표현을 임의 생성하지 않는다.

## 결과 근거 규칙

- 결과의 대표 숫자는 총 예상 혜택에서 연회비를 차감한 같은 기준기간의 `예상 순혜택`이다. 총 예상 혜택과 연회비를 바로 아래에 함께 표시한다.
- 혜택 한도는 `생활 할인 월 최대 1만 원`처럼 적용 영역과 기간을 함께 표시한다. 카드 전체 한도처럼 읽히는 포괄 라벨을 사용하지 않는다.
- 기본 결과에는 예상 순혜택, 총 예상 혜택, 연회비, 핵심 한도, 데이터 기준일을 표시한다.
- `계산 근거 보기` disclosure에는 영역별 계산식, 한도 적용 전·후, 순혜택 계산, 적용 조건, 제외·미반영 항목, 기준일·규칙 버전을 제공한다.
- 할부 등 결과 해석에 중요한 미반영 항목은 disclosure가 닫혀 있어도 짧게 고지한다.
- 최초 체크포인트에는 AI 설명과 비활성 placeholder를 만들지 않는다. 정형 근거만으로 결과 화면이 완전해야 한다.

## 완료 처리 규칙

- 이 단계에서 어떤 TASK도 GitHub Issue `Done`으로 닫지 않는다. `In progress`를 유지하고 "프로토타입 시각 확인" 체크포인트만 기록한다.
- 자동 테스트·NFR·보안·배포 Gate 통과를 이 단계의 완료 근거로 제시하지 않는다.

- 검증되지 않은 절감액·사용자 수·추천 보장 문구, 실제 카드사·플랫폼 로고 사용
- 미확정(`미확정` 표기) 항목을 에이전트 판단으로 확정하는 것 — `prototype-visual-spec.md`와 원장을 먼저 갱신한다
