# CardFit 프로토타입 시각화 계획 (정본)

## 개요

[`prototype-suggestion.md`](prototype-suggestion.md)의 **19건을 계획 정본**으로 두고, 최초 실행인 `P-VIS-01~03` 경량 시각 체크포인트를 에이전트가 착수할 수 있는 수준까지 구체화한 문서다. 19건의 계약·UX·UI 범위는 보존하되 첫 시각 검토에서는 입력 → 결과 → 핵심 근거만 구현한다.

이 문서는 `/grill-it` 세션의 산출물이며, 결정 진척은 [`docs/grill/GRILL_LEDGER.md`](../../docs/grill/GRILL_LEDGER.md)에 기록된다. `UNRESOLVED` 토픽이 남은 절은 `미확정`으로 표시하고, 미확정 항목을 에이전트가 임의로 확정하지 않는다.

기준 문서 우선순위는 `AGENTS.md`를 따른다 — 충돌 시 `법·규제·보안 → PRD → SRS → 정책 결정 로그 → TASK → 구현` 순서다.

### 목차

1. 실행 슬라이스와 산출 경계
2. 프로토타입 코드 거처와 실행 방식
3. 화면 목록과 라우팅 구조
4. UI가 바인딩할 ViewModel 타입 스케치
5. Fixture 규격과 상태 전환 수단
6. 상태 언어와 카피
7. 스코프 고지·금지어 문구
8. 입력 화면 정책
9. 결과 시나리오와 유지·변경 정책
10. 결과 요약과 근거 패널
11. 디자인 토큰과 반응형 기준 *(미확정 — T12)*
12. 시각 검토 판정과 기록 *(미확정 — T13)*
12. 결론
13. 출처

## 1. 실행 슬라이스와 산출 경계

### 1.1 확정 사항

이번 프로토타입의 계획 정본은 **계약 8건 + UX 4건 + UI 7건 = 19건**이다. 최초 코딩 범위는 아래 3개 경량 시각 체크포인트로 제한한다.

| 항목 | 결정 |
| --- | --- |
| 계획 정본 | `COMMAND-008`, `DATA-001·002`, `API-001~003`, `SPEC-001`, `MOCK-001`, `UX-001~004`, `UI-001~007` (19건) |
| 최초 실행 | `P-VIS-01` 기반 · `P-VIS-02` 입력 · `P-VIS-03` 결과와 핵심 근거 |
| 최초 참조 TASK | `UX-001~004`, `UI-001`, `UI-003`, `UI-005`, `UI-006`의 최소 조항 |
| 후속 연기 | `UI-002`, `UI-004`, `UI-007`, RANGE, AI, 상태 7종 전체, 검토자 상태 패널 |
| 계약 TASK | 19건 계획에서 유지하되 최초 시각 코딩 후 정본 의존 순서로 진행 |
| 예외 | 최초 화면은 **후보 ViewModel 타입 스케치**에 바인딩하고 `SPEC-001` 확정 시 교체 |
| 타입 스케치의 지위 | `SPEC-001` 승인 계약이 아니다. **후보(candidate)** 이며, `SPEC-001` 확정 시 이 스케치를 교체한다 |
| 금지 | 컴포넌트 파일 안에 인라인으로 화면 전용 데이터 모양을 정의하는 것 (임의 타입 결합) |

### 1.2 이 결정의 이유

19건을 정본으로 유지해 계약 기반 본 개발 연결성을 보존하되, 첫 시각 검토는 사용자가 미래지출 입력과 조건별 유지·변경 결과·근거를 이해하는지만 확인한다.

- 얻는 것: 2개 화면·3개 체크포인트로 빠른 방향 검증
- 차단하는 것: 화면·컴포넌트가 임의 데이터 모양에 결합되는 것
- 남는 위험: 타입 스케치가 `SPEC-001` 확정 계약과 어긋날 수 있다. 어긋나면 **화면이 아니라 타입 파일과 Fixture를 먼저 고친다.**

### 1.3 재작업 경계

| 계약 확정 시 바뀌는 것 | 바뀌지 않는 것 |
| --- | --- |
| §4 타입 스케치 → `SPEC-001` ViewModel | 화면 컴포넌트와 레이아웃 |
| Fixture 필드명·enum 값 | 상태 분기 구조 |
| — | 정보 위계와 읽기 순서 |

## 2. 프로토타입 코드 거처와 실행 방식

### 2.1 확정 사항

프로토타입 코드는 **저장소 루트의 Next.js App Router 앱 하나**로 만든다. 별도 앱·별도 저장소·정적 HTML로 만들지 않는다.

| 항목 | 결정 |
| --- | --- |
| 위치 | 저장소 루트 (`CardFit-prd-to-srs/`) — 문서와 같은 루트를 공유한다 |
| 스택 | Next.js App Router · TypeScript · Tailwind CSS · shadcn/ui (`AGENTS.md` 고정 기술 구조) |
| 패키지 매니저 | `npm` |
| 실행 | `npm run dev` 한 번으로 프로토타입 진입 화면이 열린다 |
| `src/` 디렉터리 | 사용하지 않는다 — 루트 `app/`을 쓴다 |
| 이 앱의 지위 | 버리는 목업이 아니라 **본 개발이 이어받는 같은 앱**이다 |

### 2.2 디렉터리 배치

```
CardFit-prd-to-srs/
├─ app/                  # Next.js App Router — 프로토타입 화면
├─ components/           # 공통 UI. shadcn/ui 컴포넌트 포함 (UI-001 산출물)
├─ lib/                  # ViewModel 타입 스케치, Fixture 로더 (§4·§5에서 확정)
├─ fixtures/             # 비식별 정적 Fixture (§5에서 확정)
├─ public/
├─ package.json · tsconfig.json · components.json · next.config.ts
└─ PRD/ · SRS-Drafts/ · TASK/ · plans/ · reports/ · landing/   # 기존 문서 자산 (변경 없음)
```

`.gitignore`는 이미 `node_modules/`, `.next/`, `.vercel/`, `coverage/`, `playwright-report/`, `test-results/`를 제외하고 있어 추가 작업이 필요하지 않다.

### 2.3 이 단계에서 만들지 않는 것

부트스트랩 시 기본 생성되더라도 다음은 이번 단계에서 **작성·연결하지 않는다**.

- Route Handler(`app/api/**`), Server Action, Prisma, Supabase 클라이언트, 환경변수 의존 코드
- 인증·세션·미들웨어
- 배포 설정(Vercel 프로젝트 연결)

## 3. 화면 목록과 라우팅 구조

### 3.1 확정 사항

최초 경량 체크포인트는 **2개 주요 라우트**만 구현한다.

| 라우트 | 사용자 목적 | 포함 화면·상태 |
| --- | --- | --- |
| `/plan` | 미래지출과 카드 제약 입력 | 미래지출 입력, 입력 오류 |
| `/result` | 조건별 결과를 비교하고 핵심 근거 확인 | 세 시나리오 결과, 정형 근거 6개, 기준일·미반영 항목 |

### 3.2 전환 원칙

- 기본 사용자 흐름은 `/plan` → `/result`다.
- 세부 상태마다 별도 URL을 만들지 않는다. 같은 라우트 안에서 명시적인 ViewModel 상태로 전환한다.
- 새로고침하거나 주요 라우트에 직접 접근해도 해당 단계의 대표 Fixture가 표시되어 시각 검토가 가능해야 한다.
- 이전·다음 CTA로 연속 흐름을 제공하되 브라우저 뒤로가기를 막지 않는다.
- `/`, `/onboarding`, 검토자 상태 패널은 후속 체크포인트로 미룬다.

### 3.3 이 결정의 이유

입력·결과 두 지점만 직접 접근 가능하게 해 최초 검토 비용을 줄인다. 연기된 온보딩·상태·선택 화면은 19건 계획에서 삭제하지 않는다.

## 4. UI가 바인딩할 ViewModel 타입 스케치

### 4.1 타입 원천과 지위

화면 데이터 타입의 단일 진입점은 `features/cardfit-prototype/lib/view-model.ts`다. 이 파일은 `SPEC-001` 승인 계약이 아니라 로컬 시각 프로토타입용 **후보 ViewModel**이며, 파일 상단에 그 지위를 주석으로 명시한다.

- 컴포넌트와 Fixture는 이 파일에서 타입을 import한다.
- 컴포넌트 파일 안에 화면 전용 데이터 타입을 다시 정의하지 않는다.
- 이후 `SPEC-001`이 확정되면 화면보다 이 타입과 Fixture를 먼저 계약에 맞춘다.
- 영속 엔터티나 API DTO를 흉내 내지 않고, 화면이 읽고 판단하는 최소 필드만 둔다.

### 4.2 타입 구성

하나의 거대한 객체 대신 기능별 ViewModel과 공통 상태 타입을 조합한다.

```ts
type PrototypeScreenStatus =
  | "loading"
  | "empty"
  | "partial"
  | "stale"
  | "error"
  | "unavailable"
  | "success";

interface PrototypeMetaViewModel {
  fixtureId: string;
  status: PrototypeScreenStatus;
  dataAsOf: string | null;
  isExample: true;
}

interface OnboardingViewModel {
  meta: PrototypeMetaViewModel;
  platformStatus: "connected" | "partial" | "stale" | "expired" | "disconnected";
  canContinue: boolean;
}

interface PlanInputViewModel {
  meta: PrototypeMetaViewModel;
  inputMode: "single" | "range";
  categories: FutureSpendCategoryViewModel[];
  constraints: CardConstraintViewModel;
}

interface ResultViewModel {
  meta: PrototypeMetaViewModel;
  activeScenario: "low" | "base" | "high";
  scenarios: ScenarioResultViewModel[];
  evidence: EvidenceViewModel;
  selection: SelectionViewModel;
}
```

위 코드는 필드명을 영구 확정하는 API 계약이 아니라 구현 시 지켜야 할 구조의 기준이다. 하위 타입의 구체 필드는 T5~T11 결정이 반영될 때 같은 파일과 이 절에 보완한다.

### 4.3 상태 모델링 원칙

- `status`는 문자열을 임의로 추가하지 않고 `PrototypeScreenStatus`의 7종만 사용한다.
- 상태별 필수 데이터 차이가 크면 선택 필드를 늘어놓지 말고 판별 가능한 유니온으로 좁힌다.
- 모든 Fixture에는 `fixtureId`, `status`, `isExample: true`를 포함해 실제 사용자 데이터처럼 오인되지 않게 한다.
- 화면 전환 상태와 금융 계산 결과를 컴포넌트에서 새로 계산하지 않는다.

## 5. Fixture 규격과 상태 전환 수단

### 5.1 Fixture 위치와 형식

정적 예시 데이터는 `features/cardfit-prototype/fixtures/` 아래의 TypeScript 모듈로 관리한다.

```text
features/cardfit-prototype/fixtures/
├─ onboarding.ts
├─ plan.ts
└─ result.ts
```

- 각 Fixture는 `features/cardfit-prototype/lib/view-model.ts`의 대응 ViewModel 타입을 만족해야 한다.
- 정상·부분·오래됨·실패뿐 아니라 유지·변경처럼 시각 검토에 필요한 결과 변형을 이름 있는 Fixture로 둔다.
- 실제 사용자·카드 데이터와 실제 절감액을 사용하지 않는다.
- 모든 Fixture에는 §4의 `fixtureId`, `status`, `isExample: true` 메타데이터를 포함한다.
- Fixture 선택과 화면 상태 전환은 프로토타입 표현을 위한 것이며 계산 로직을 흉내 내지 않는다.

### 5.2 상태별 직접 접근

검토 상태는 URL query로 재현한다. 예시는 다음과 같다.

```text
/result?state=success
/result?state=partial
/result?state=stale
/result?state=error
```

- 같은 URL을 새로고침하거나 공유해도 같은 Fixture 상태가 표시되어야 한다.
- 알 수 없거나 허용되지 않은 `state` 값은 해당 라우트의 대표 Fixture로 안전하게 되돌린다.
- 일반 사용자 화면에는 상태를 선택하는 UI를 제공하지 않는다. 사용자는 시스템이 제시한 상태와 복구 행동만 경험한다.

### 5.3 개발자·검토자 전용 패널

`?review=1`일 때만 접이식 `프로토타입 검토` 패널을 표시한다.

- 패널은 개발자와 시각 검토자가 Fixture를 빠르게 바꾸는 테스트 리모컨이다.
- 사용자 인터뷰 참가자는 패널을 조작하지 않는다. 진행자가 상태별 URL을 미리 열어 준다.
- 패널 선택은 `state` query를 갱신해 현재 상태를 링크로 재현할 수 있게 한다.
- 패널은 기본 사용자 흐름에서 숨기며 실제 서비스 기능으로 승격하지 않는다.
- 본 개발 전환 시 제거 여부를 확인하고, 배포 대상 UI에 검토 패널이 남지 않도록 별도 Gate로 검사한다.

### 5.4 역할 경계

| 역할 | 상태와의 상호작용 |
| --- | --- |
| 일반 사용자·인터뷰 참가자 | 주어진 데이터 상태를 확인하고 안내된 복구 행동을 수행한다 |
| 인터뷰 진행자 | 검토 목적에 맞는 상태별 URL을 미리 준비한다 |
| 개발자·시각 검토자 | `review=1` 패널에서 Fixture 상태를 전환하고 링크를 공유한다 |

## 6. 상태 언어와 카피

### 6.1 문체 원칙

뱅크샐러드의 사용자-facing 문체처럼 문맥에 따라 해요체와 합니다체를 구분한다.

| 문구 종류 | 문체 | 적용 원칙 |
| --- | --- | --- |
| 상태 제목·진행 상태·일반 안내 | 차분한 해요체 | 사용자가 현재 상황을 빠르게 이해하도록 짧게 쓴다 |
| 계산 사실·데이터 기준·금융 조건·스코프·주의사항 | 합니다체 | 판단 조건과 제품 책임 경계를 단정하고 정확하게 전달한다 |
| CTA | 행동형 명사구 | `다시 시도하기`, `미래지출 입력하기`처럼 결과를 예측할 수 있게 쓴다 |

- 혜택·정확성·발급 가능성을 보장하는 표현을 사용하지 않는다.
- 사용자 잘못처럼 들리는 표현이나 내부 오류 코드를 노출하지 않는다.
- 제목은 상태, 본문은 원인·영향·다음 행동 순서로 쓴다.
- 같은 컴포넌트 계층에서 해요체와 합니다체를 임의로 섞지 않는다.

### 6.2 공통 상태 사전

| 상태 | 의미 | 대표 제목 | 기본 CTA |
| --- | --- | --- | --- |
| `loading` | 처리 중 | 계산 결과를 준비하고 있어요 | 없음 |
| `empty` | 사용자가 아직 필요한 값을 입력하지 않음 | 아직 입력한 미래지출이 없어요 | 미래지출 입력하기 |
| `partial` | 필수 데이터 일부를 확인하지 못해 결과 공개 불가 | 일부 데이터를 확인할 수 없어요 | 데이터 확인하기 |
| `stale` | 최신 데이터는 아니지만 기준일이 있는 기존 데이터로 결과 공개 가능 | 최근 확인된 데이터가 있어요 | 데이터 다시 확인하기 |
| `error` | 재시도로 복구될 수 있는 일시적 실패 | 정보를 불러오지 못했어요 | 다시 시도하기 |
| `unavailable` | 동의 만료·연결 해제 등 선행 조건 복구 전 기능 사용 불가 | 지금은 계산을 진행할 수 없어요 | 연결 상태 확인하기 |
| `success` | 정상 완료 | 계산이 완료됐어요 | 결과 확인하기 |

### 6.3 상태별 본문 원칙

- `empty`는 정상적인 미입력 상태이며 조회 실패나 보유카드 0건의 대체 표현으로 쓰지 않는다.
- `partial`에서는 PRD US-A AC8에 따라 어느 시나리오의 추천 결과도 노출하지 않는다.
- `stale`에서는 `최근 확인된 데이터를 기준으로 계산했습니다`와 데이터 기준일을 함께 표시한다.
- `error`는 일시적 실패와 재시도 행동을, `unavailable`은 복구해야 할 선행 조건을 각각 설명한다.
- `success`는 완료 사실만 알리고 유리함·정확함·절감 보장을 암시하지 않는다.
- 화면별 보충 설명은 달라질 수 있지만 대표 제목·상태 의미·기본 CTA는 이 사전을 따른다.

## 7. 스코프 고지·금지어 문구

### 7.1 문구의 지위

이번 프로토타입은 `COMMAND-008`을 착수하지 않으므로 아래 문구는 PRD ADR-002와 GR4를 시각 검토하기 위한 **후보 문구**다. 승인된 정책 계약이 아니며, 본 개발에서 `COMMAND-008` 문구가 확정되면 우선 교체한다.

### 7.2 온보딩 고지

```text
CardFit은 예상 지출을 바탕으로 카드 조합별 혜택을 비교합니다.

계산 결과는 입력한 금액과 최근 확인된 카드 정보를 기준으로 합니다.
카드 신청·발급·해지를 대신 진행하지 않습니다.
```

### 7.3 조합 선택 고지

```text
이 조합을 선택해 저장합니다.

조합을 저장해도 카드 신청이나 해지가 완료되지는 않습니다.
실제 변경 여부와 조건은 각 카드사에서 확인해야 합니다.
```

### 7.4 외부 이동 고지

```text
카드사 공식 화면으로 이동합니다.

이동 후 연회비·전월 실적·발급 조건을 다시 확인해 주세요.
CardFit은 신청서 작성·제출 또는 카드 해지를 대신하지 않습니다.
```

### 7.5 금지 표현

- `자동으로 카드를 바꿔드려요`
- `카드를 대신 해지해 드려요`
- `이 카드가 무조건 가장 유리합니다`
- `혜택을 보장합니다`
- 외부 카드사 처리가 끝나지 않았는데 `신청이 완료됐어요`라고 표현하는 문구
- 그 밖에 신청·발급·해지 대행, 확정 수익·혜택, 실행 완료를 암시하는 변형 표현

### 7.6 표시 원칙

- 온보딩 고지는 입력 전 확인할 수 있게 하고 외부 이동 고지는 이동 직전 다시 표시한다.
- 조합 저장과 실제 카드 행동을 서로 다른 완료 상태로 표현한다.
- 고지 본문은 §6에 따라 합니다체를 사용한다.
- 후보 문구임을 사용자 화면에 표시하지 않는다. 후보 지위는 문서와 코드 주석으로 관리한다.
- 프로토타입 시각 검토에서는 금지 표현 노출 0건을 확인하되 `COMMAND-008` 승인으로 보고하지 않는다.

## 8. 입력 화면 정책

### 8.1 초기값 정책

과거 소비 이력이 없거나 이번 프로토타입처럼 실제 개인 데이터를 연결하지 않은 경우 미래지출 금액은 **빈 값으로 시작**한다.

- 검증되지 않은 업계 평균이나 개인화 값을 자동 입력하지 않는다.
- 사용자가 `예시 금액 적용하기`를 명시적으로 선택한 경우에만 비개인화 예시 값을 입력한다.
- 적용된 예시 값은 사용자가 자유롭게 수정·삭제할 수 있다.
- 예시 값이 적용된 동안 개인 소비 데이터나 업계 통계를 기준으로 하지 않았음을 입력 영역 가까이에 표시한다.
- 사용자가 예시 값을 그대로 제출하더라도 계산 전에 예시 적용 상태를 인지할 수 있어야 한다.
- 업계 평균 분기는 출처·기준일·최신성·편향 검토가 승인된 뒤 M2 별도 변경 요청으로만 활성화한다.

### 8.2 프로토타입 예시

```text
예상 지출 금액

[                         ]
직접 입력하거나 예시 금액을 적용할 수 있어요.

[예시 금액 적용하기]
```

예시 적용 후:

```text
예상 지출 금액

[ 1,200 ] 만 원

이 금액은 입력 방법을 확인하기 위한 예시이며,
개인 소비 데이터나 업계 통계를 기준으로 하지 않았습니다.

[예시 지우기]
```

### 8.3 입력 단계와 모드

`/plan` 내부를 주소 이동 없는 2단계로 구성한다.

1. 미래지출 입력
2. 카드 조건 확인

- 미래지출은 `SINGLE`을 기본으로 한다.
- `RANGE`는 사용자가 `범위로 입력하기`를 선택할 때 같은 화면에서 최소·예상·최대 입력으로 펼친다.
- RANGE는 세 입력에 같은 만원 단위를 사용하고 `최소 ≤ 예상 ≤ 최대`를 입력 중 검증한다.
- 카드 조건은 최대 카드 수·연회비 한도·신규 발급 허용 여부를 미래지출과 분리해 두 번째 단계에서 확인한다.

### 8.4 카테고리 선택

기본 경로는 자유 문구가 아니라 선택형 대분류다.

| 카테고리 | 포함 예시 |
| --- | --- |
| 주거 | 보증금·월세·관리비 변화 |
| 가구·가전 | 가구·가전 구매 |
| 예식 | 웨딩홀·촬영·예복 등 |
| 여행 | 신혼여행·장기 여행 |
| 교통 | 차량·대중교통 변화 |
| 생활비 | 식비·생필품 등 반복 지출 변화 |
| 교육 | 교육·학습 비용 |
| 의료 | 병원·건강 관련 비용 |
| 기타 | 위 대분류에 속하지 않는 사용자 직접 입력 |

- `신혼 가구`, `신혼여행`처럼 이벤트가 포함된 좁은 이름을 필수 입력으로 요구하지 않는다.
- `기타`를 선택한 경우에만 직접 입력란을 표시해 PRD F-08의 자유 카테고리 경로를 보존한다.
- 실제 카드 혜택 분류 체계와의 매핑은 이번 시각 프로토타입에서 확정하지 않는다.

### 8.5 금액 입력

금액 입력 단위는 **만원으로 고정**한다. `원·만 원·억 원` 전환 탭을 만들지 않는다.

```text
예상 금액

[ 1,200                      ] 만 원

12,000,000원 · 1,200만 원

[+10만] [+100만] [+1,000만]
```

- 모바일에서는 숫자 키패드를 사용하고 입력값에 천 단위 구분을 표시한다.
- 내부 ViewModel 값은 원 단위 정수로 정규화하고 화면에서는 만원 단위 입력값과 전체 원 금액을 함께 표시한다.
- 금액이 1억 원 이상이면 읽기 보조용 억 단위 표현도 병기한다. 예: `30,000만 원 · 3억 원`.
- 빠른 금액 버튼은 현재 값에 해당 금액을 더하고 실행 취소·금액 지우기를 제공한다.
- 입력값에 붙여넣은 쉼표와 공백은 정리하되 음수·비숫자·정책 상한 초과는 오류로 처리한다.
- 단위 탭 전환과 소수 입력 규칙은 만들지 않는다.

### 8.6 접근성·오류 처리

- 단위·선택 상태·오류를 색상에만 의존해 구분하지 않는다.
- 환산 금액은 입력값과 연결된 설명으로 제공하되 숫자를 누를 때마다 screen reader가 과도하게 반복하지 않게 한다.
- RANGE 순서 오류는 제출 후가 아니라 입력 중 표시하고 해당 값은 계산 상태로 넘기지 않는다.
- 오류 후에도 입력값과 선택 상태를 유지하고 첫 오류 필드로 focus를 이동한다.

### 8.7 추가 확인 항목

입력 화면과 관련해 프로토타입 착수 전에 남은 Grill 토픽은 없다. 실제 제품 상한은 `DECISION-007` 해소 전까지 미확정이다.

### 8.8 할부 범위 경계

- 프로토타입에서는 일시불·할부 선택과 할부 개월을 입력받지 않는다.
- 사용자는 `예상 지출 총액`과 `지출 예정 시기`만 입력한다.
- 화면과 Fixture는 할부의 월별 실적·혜택·수수료를 계산한다고 암시하지 않는다.
- 결과 근거의 `이 계산에 포함되지 않은 항목`에 할부 수수료, 월별 실적 반영 차이, 카드사별 무이자 할부 조건을 표시한다.
- `일시불 기준으로 계산했습니다`처럼 미확정 귀속 정책을 확정하는 문구도 사용하지 않는다.
- 본 개발에서 할부를 지원하려면 `DECISION-005`를 먼저 해소하고 데이터·계산·테스트 계약을 함께 변경한다.

### 8.9 미래지출 항목 구조

- 미래지출은 여러 건 추가·수정·삭제할 수 있으며 한 건 이상 있어야 카드 조건 단계로 이동한다.
- 사용자는 `한 번 쓰는 금액`(`ONE_TIME`)과 `매달 쓰는 금액`(`MONTHLY`) 중 지출 형태를 선택한다.
- `ONE_TIME`은 예상 지출 총액과 지출 예정 연·월을 입력한다.
- `MONTHLY`는 앞으로 예상하는 월 금액과 변경 시작 연·월을 입력한다.
- 증가·감소 방향을 사용자에게 별도로 묻지 않는다. 비교 가능한 과거 월평균 Fixture가 있으면 미래 월 금액과의 차이로 방향·차액을 표시한다.
- 과거 기준값이 없으면 `비교할 과거 지출이 없어요`라고 표시하고 방향을 임의 생성하지 않는다.
- `confidence`는 값과 사용자 효용이 미정이므로 프로토타입 화면과 후보 ViewModel에서 제외한다. 후속 데이터 계약에서 enum·용도가 확정될 때만 추가한다.
- 월별 반복 금액을 12개월 혜택 계산에 귀속하는 규칙은 D6 승인 대상이며, 프로토타입이 실제 계산 정책을 확정하지 않는다.

예시:

```text
카테고리       생활비
지출 형태      매달 쓰는 금액
최근 월평균    80만 원 (예시 데이터)
앞으로 예상    110만 원
변경 시작      2026년 10월
예상 변화      월 30만 원 증가
```

### 8.10 입력 상한 경계

- 프로토타입에서 최대 입력 금액·카테고리별 상한·ONE_TIME/MONTHLY별 상한을 임의로 정하지 않는다.
- 빈 값·0원·음수·비숫자·RANGE 순서 오류만 프로토타입 입력 검증 대상으로 삼는다.
- 상한 초과 오류 상태와 상한 안내 문구는 프로토타입에서 구현하지 않는다.
- 본 개발에서는 대상 사용자 금액 분포·계산 성능·데이터 타입을 근거로 `DECISION-007`을 승인한 뒤 입력 계약과 오류 문구를 함께 추가한다.

## 9. 결과 시나리오와 유지·변경 정책

### 9.1 시나리오 탭

화면에는 짧은 사용자 언어를 사용하고 내부 계약 값은 유지한다.

| 내부 값 | 화면 라벨 | 접근성 이름 |
| --- | --- | --- |
| `LOW` | 더 적게 | 예상 지출보다 적게 쓸 때 |
| `BASE` | 예상한 만큼 | 예상한 만큼 쓸 때 |
| `HIGH` | 더 많이 | 예상 지출보다 많이 쓸 때 |

- 기본 선택은 `BASE`, 즉 `예상한 만큼`이다.
- 탭은 키보드와 screen reader로 조작할 수 있어야 하며 선택 상태를 색상에만 의존해 표시하지 않는다.
- 결과 제목이나 설명에는 `예상 지출보다 적게 쓸 때`처럼 맥락을 포함해 짧은 탭 라벨만 떼어 읽어도 의미가 손실되지 않게 한다.

### 9.2 유지·변경 판정

- 현재 조합과 변경 조합의 계산 결과가 같으면 `유지`로 분류한다.
- 동률일 때 `유지가 유리해요`처럼 우월성을 주장하지 않고 `현재 조합을 유지해도 예상 혜택 차이가 없습니다.`라고 설명한다.
- `유지`와 `변경`은 모두 정상적인 계산 결과이며, 변경을 성공이나 축하 상태로 더 강조하지 않는다.
- 결론에는 예상 차액, 통화 단위, 비교 기준기간을 함께 표시한다.
- `LOW`·`BASE`·`HIGH`는 사용자가 선택한 지출 조건이지 결과의 좋고 나쁨을 뜻하지 않는다.

### 9.3 다중 변경 후보 동률 경계

여러 변경 후보끼리 결과가 같은 경우의 정렬·대표 후보 선택 규칙은 아직 확정하지 않는다. 최초 `P-VIS-03`은 다중 변경 후보 순위를 표시하지 않으며, Fixture나 UI가 임의 순위를 만들지 않는다. 이 정책이 승인되기 전에는 동률 후보에 `1위`·`최적` 등의 표현을 사용하지 않는다.

## 10. 결과 요약과 근거 패널

### 10.1 기본 결과 요약

대표 숫자는 총 할인액이 아니라 연회비를 차감한 **예상 순혜택**이다. 결과 카드의 기본 노출 순서는 다음과 같다.

1. 예상 순혜택
2. 총 예상 혜택과 연회비
3. 결과에 가장 크게 영향을 준 혜택 한도
4. 데이터 기준일
5. `계산 근거 보기` disclosure

```text
예상 순혜택
연 15만 3천 원

총 예상 혜택  연 16만 2천 원
연회비        연 9천 원

생활 할인은 월 최대 1만 원까지 적용됩니다.
데이터 기준  2026.08.27

[계산 근거 보기]
```

- `혜택 한도 월 1만 원`처럼 카드 전체에 적용되는 것으로 오해할 표현을 사용하지 않는다.
- `생활 할인 월 최대 1만 원`, `온라인 쇼핑 할인 월 최대 2만 원`처럼 **적용 영역과 한도 기간**을 함께 표시한다.
- 한도가 없는 혜택과 한도가 있는 혜택이 함께 있으면 각각 구분한다.
- 예상 혜택·연회비·순혜택은 모두 같은 기준기간으로 환산해 표시한다.

### 10.2 펼친 계산 근거

`계산 근거 보기`를 펼치면 정형 근거 6종을 다음 순서로 표시한다.

1. 영역별 예상 혜택 계산식
2. 영역별 또는 공유 혜택 한도와 한도 적용 전·후 금액
3. 연회비와 예상 순혜택 계산
4. 전월 실적 등 적용 조건
5. 제외·미반영 항목
6. 데이터 기준일과 계산 규칙 버전

```text
생활 할인
계산상 할인           월 12,500원
월 통합 한도 적용    -월  2,500원
실제 적용             월 10,000원

총 예상 혜택          연 162,000원
연회비                -연   9,000원
예상 순혜택            연 153,000원
```

- disclosure는 키보드로 열고 닫을 수 있고 `aria-expanded`와 연결된 제목을 제공한다.
- 계산에 포함되지 않은 할부 조건 등 결과 해석에 중요한 경계는 접힌 상태에서도 짧게 고지한다.
- 실제 상품명·수치는 승인된 Fixture가 있을 때만 사용한다. 분석 예시는 화면 구조를 설명하는 근거이지 프로토타입의 실제 카드 추천 데이터가 아니다.

### 10.3 AI 영역

최초 `P-VIS-03`에서는 AI 설명 영역과 비활성 placeholder를 모두 만들지 않는다. 정형 근거만으로 결과 화면이 완전해야 한다. M2에서 `COMMAND-009`가 승인되면 정형 계산을 바꾸지 않는 보조 설명 계층으로 별도 추가한다.
