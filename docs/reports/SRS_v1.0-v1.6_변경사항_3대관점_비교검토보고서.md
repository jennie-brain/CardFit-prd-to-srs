## 기술 요약

v1.0에서 v1.6으로의 변화는 기능 수를 늘린 개정이라기보다, **구현 전제가 불명확한 제품 요구사항을 초급 개발자와 AI 보조 개발이 실행할 수 있는 단계별 시스템 명세로 전환한 것**에 가깝다. 기능 요구사항은 두 문서 모두 13개이고 비기능 요구사항도 9개로 유지되지만, 최신본은 기술 스택·외부 연동 경계·배포 방식·비용 상한·단계별 합격 조건을 구체화했다.

가장 중요한 변화는 다음 세 가지다.

1. **기술 스택이 선택지에서 제약조건으로 바뀌었다.** 최신본은 Next.js App Router, Prisma, Supabase, Tailwind CSS, shadcn/ui, Vercel AI SDK, Gemini, Vercel 배포를 C-TEC-001~007과 하위 기술 요구사항으로 고정했다.
2. **MVP의 성공 기준이 12개 기능 일괄 구현에서 핵심 가치 7개 경로 우선 구현으로 바뀌었다.** M0~M3 단계가 추가되면서 Gemini·Cron·실제 플랫폼 연동·업계 평균 초기값은 초기 포트폴리오 MVP의 합격 조건에서 제외됐다.
3. **제품 가치의 핵심은 유지됐다.** 미래지출을 반영해 카드 조합 또는 유지 결론과 차액·근거를 제공한다는 가치는 유지되며, 추천안 이행 확인은 가치 전달 이후의 측정 기능으로 분리됐다.

종합적으로 최신본은 구현 가능성·비용 통제·기술적 정직성이 크게 향상됐다. 다만 Net Benefit의 9개 정책 항목, 실제 Platform Adapter 계약, 카드 상태 의미와 컴플라이언스 승인은 아직 확정되지 않았으므로 실제 서비스 통합 가능성까지 증명한 문서는 아니다.

## 2. 기술 스택이 구현 가능한 제약조건으로 명확해졌다

v1.0은 기능과 데이터 구조는 설명했지만 특정 프레임워크·DB·배포 환경을 구현 기준선으로 고정하지 않았다. v1.6은 단일 풀스택 구조와 허용·금지 기술 경계를 정의해 AI가 서로 다른 아키텍처를 임의 생성할 가능성을 줄였다.

### 2.2 기술 스택 관점의 결론

**명확성은 크게 개선됐다.** 최신본은 기술 이름만 나열하지 않고 사용 위치, 금지 대안, 환경 분리, 장애 시 동작과 검증 조건을 함께 명시한다. 특히 계산 로직을 TypeScript 도메인에 격리하고 AI를 설명 전용으로 제한한 결정은 금융 계산의 재현성을 보호한다.

다만 다음 조건은 여전히 기술 스택만으로 해결되지 않는다.

- 실제 뱅크샐러드 내부 연동이 전용망·mTLS·고정 IP를 요구하면 Vercel 단일 배포 제약과 충돌할 수 있다.
- Supabase Preview DB를 M2까지 만들지 않는 설계는 비용에는 유리하지만, M1 Preview가 Production 데이터를 쓰지 않도록 Fixture·읽기 전용 설정을 엄격히 검증해야 한다.
- Gemini 모델명과 가격은 변경될 수 있으므로 `AI_MODEL` 환경 변수와 월 비용 실측을 기준으로 운영해야 한다.

## 3. MVP가 전체 기능 구현에서 핵심 판단 경험 검증으로 조정됐다

v1.0은 포함 기능 12개를 하나의 MVP 범위로 다뤘다. v1.6은 사용자가 실제로 가치를 느끼는 판단 흐름을 먼저 검증하고, 데이터 영속화·자동 관측·실제 통합을 후속 단계로 분리했다.

### 3.2 핵심 가치가 훼손되지 않았는지에 대한 판정

**핵심 가치는 보존됐다.** 사용자는 최신본의 M0~M1만으로도 미래지출을 입력하고 세 가지 예상 범위에서 현재 카드 유지 또는 변경 결론, 예상 차액과 최소 6개 근거를 확인할 수 있다. Gemini·Cron·실제 마이데이터 후속 관측은 이 판단을 만들어내는 데 필수적이지 않으므로 M2 이후로 이동해도 1차 가치 전달은 손상되지 않는다.

반면 다음 항목은 “기능이 삭제된 것”이 아니라 “M1 합격에서 제외된 것”이다.

| 후속 기능 | 이동 단계 | 이동 이유 | 핵심 가치에 미치는 영향 |
| --- | :---: | --- | --- |
| 업계 평균 초기값 | M2 이후 별도 승인 | 출처·최신성·편향 미검증 | 입력 편의는 줄지만 판단 정확성과 정직성은 높아짐 |
| Gemini 설명 | M2 선택 | 정형 근거만으로 핵심 설명 가능 | 핵심 가치 영향 없음 |
| Vercel Cron 자동 이행 관측 | M2 | 시간·상태·동의·멱등성 복잡성 | 결과 이후 측정이 늦어질 뿐 최초 판단 경험에는 영향 없음 |

### 5.3 검토의 한계

이 비교는 저장소의 SRS 문서 두 개를 대상으로 한 정적 문서 분석이다. 실제 코드, 배포 로그, 내부 API 계약, 사용자 테스트 결과를 검증한 것은 아니다. 따라서 “구현 가능한 구조로 명세됐다”는 판단은 가능하지만 “실제로 구현·운영됐다”거나 “제품 가치가 실사용자에게 검증됐다”는 결론은 내릴 수 없다.

또한 문서 줄 수와 다이어그램 수는 구조 변화의 규모를 설명하기 위한 보조 지표다. 수가 많다고 요구사항의 품질이 자동으로 높아지는 것은 아니며, 핵심 판정은 각 요구사항의 검증 가능성과 단계별 완료 조건을 기준으로 내렸다.

1. M0에서 사용할 카드 10~20개와 혜택 규칙 2~3종의 선정 기준은 무엇인가?
2. Net Benefit 임계값은 절대 금액, 예상 혜택 대비 비율 또는 사용자별 전환 마찰을 반영한 값 중 무엇으로 결정할 것인가?
3. `더 적게 쓸 때`와 `더 많이 쓸 때`의 변동 폭은 고정 비율인가, 사용자가 직접 입력하는 범위인가?
4. M1을 포트폴리오 시연으로만 사용할 것인지, 외부 사용자가 접속하는 공개 베타까지 포함할 것인가?
5. M2의 마이데이터 후속 관측 목적이 기존 동의 범위에 포함되는지 누가 승인할 것인가?

## 7. 결론

v1.0은 제품 요구사항·KPI·API·데이터 모델을 폭넓게 담은 초기 SRS였지만, 특정 기술 스택과 구현 순서가 없어 초급 개발자가 모든 기능을 동시에 구현하려 할 가능성이 컸다. v1.6은 C-TEC-001~007, Platform Adapter, M0~M3, 환경별 비용 상한과 실패 시 fallback을 추가해 구현 기준선으로서의 명확성을 높였다.

MVP의 핵심 가치도 훼손되지 않았다. 최신본은 미래지출에 따른 세 가지 예상 범위, 유지·변경 결론, 차액과 근거를 M0~M1에서 그대로 제공한다. 자동 초기값·AI 설명·+30일 관측·실제 내부 연동을 후속 단계로 이동한 것은 가치 삭제가 아니라 검증 순서의 조정이다.

따라서 최신본은 최초본보다 **기술 스택의 명확성, 초급자 구현 가능성, 비용 통제, 포트폴리오 설명력과 측정 신뢰도에서 우수하다.** 다만 Net Benefit 정책과 실제 통합 계약이 미확정이므로 M0 착수 전에 계산 규칙을 먼저 고정하고, 실제 도입 가능성은 계속 `CONDITIONAL`로 관리해야 한다. 세 가지 지출 시나리오의 사용자 친화적 명칭은 잠정 합의 상태이므로 다음 SRS 개정에서 `Proposed`로 반영하는 것이 적절하다.
